# macOS Call Routing MVP: Production Integration Plan

- Status: Proposal for owner review; no production routing is authorized by this document.
- Scope: macOS 14+ arm64/x64. Windows remains a separate feasibility decision under ADR 0015.
- Architecture gates: ADR 0015 is Proposed. ADR 0006 requires a separate decision for microphone capture and a second output clock. ADR 0016 accepts the optional macOS component architecture, but not production installation or distribution.

## Goal and honest MVP boundary

While the user has explicitly started call routing, clicking a library sound should keep ordinary local playback and also send that sound with the physical microphone to a selected compatible virtual output. The call app must use the corresponding virtual input. Stopping routing must close microphone capture and virtual output; local playback must continue. An installed or detected device, an open CPAL stream, and a local loopback are not evidence that Discord or Meet participants heard both sources.

The first MVP uses a manually installed compatible device, including the development-only ScreamPad Audio 2ch package. In-app driver installation and a public branded package remain behind ADR 0016's signing, GPL, lifecycle, and release gates. The MVP cannot promise zero call-app setup: macOS cannot choose another application's input device for the user.

## Current seams

- `audio/engine.rs` and `infrastructure/audio/cpal_backend.rs` own one always-running **default local output**. Keep that path and its device recovery independent of call routing.
- `application/playback.rs` validates managed media, decodes/caches it for the local output format, and applies per-sound mode and gain. A second output can have a different rate and clock; the existing `Arc<Clip>` cannot simply be pushed into it. Reuse the validation and decode policy, with a route-specific format/cache budget, rather than read untrusted library paths from the callback.
- `application/device_discovery.rs` and `commands/devices.rs` already expose CPAL host-qualified IDs, roles and coarse configuration status. A route start must re-enumerate and revalidate the selected ID and stream configuration. Names and `DeviceType` are advisory, and an unknown device requires explicit user selection. Never auto-select a physical output or fall back to the system default output.
- `features/settings/audioRoutingState.ts` stores selection only for the session. It does not represent a running route. The backend must be the authority for route state; the UI must not infer it from selection or a click.
- `examples/mic_route_probe.rs` is isolated feasibility code, not a production service. Port reviewed queue/mapping/conversion ideas into small tested modules; do not invoke or embed the example at runtime.

## Proposed runtime contract

Create a separate `CallRouteService` owned by Tauri application state, with a dedicated non-real-time control thread that owns CPAL streams. It must not replace or stop `AudioEngine`. The user chooses the virtual output ID in Settings and presses **Start routing**. Only that command may open microphone capture; inspect the current system-default input at start, show its identity, and never change system defaults. Reject it if it is the route device or is reported virtual; if its type is unknown, require explicit confirmation instead of assuming it is physical. Add an explicit microphone picker if the default input is unsuitable. Reject an output that is missing, lacks the required input/output roles or usable format, is physical, or has the same ID as the local engine's current output. If the local default output changes to the selected route device while routing is active, stop the route and explain the conflict. Do not route to an arbitrary unknown device without the user's explicit choice and a clear warning.

Start atomically from the user's perspective: validate devices and formats, build bounded queues and streams, start both, then report `active`. If any step fails, drop all newly opened streams, clear queued samples, and report a typed failure. On Stop, app exit, stream error, or selected-device loss, stop both streams, clear queues, release capture, and publish `stopped` or `failed`. Ignore stale callbacks/events from a previous generation. A failed route must not stop local playback. Device refresh while active must not silently switch the destination; a missing selected device stops routing.

The microphone stream writes normalized mono `f32` frames to a bounded single-producer/single-consumer ring. The virtual-output callback reads it, mixes decoded clip frames, clamps output, and maps to the selected channel/sample format. On a full ring the producer drops incoming frames and counts them; when backlog exceeds the target, the consumer discards old queued frames to cap latency. Underflow emits silence for missing frames and counts them. Independently clocked streams require occupancy feedback and bounded drift correction; equal nominal sample rates do not establish clock sync. Clip scheduling, resampling, and `Arc` retirement happen off the callback. No callback may allocate/deallocate, block, lock, log, perform I/O, or call IPC. Keep source/output levels, occupancy, overflow, underflow, dropped frames, drift and stream errors as bounded counters sampled outside callbacks; do not record microphone samples.

The local engine remains the **only** local monitoring path. When a sound is triggered during an active route, send the same logical sound to local playback and to the route using its stored gain and play mode, with an explicit result for each destination. Route failure must not turn a successful local Play into silence or claim that the call heard the clip. Stop Sound and Stop All must stop corresponding voices in both paths. While routing is off, the existing playback behavior and IPC result remain intact. No microphone samples enter local playback.

## Reviewable change sequence

1. **Architecture approval.** Accept or amend ADR 0015 for this narrow macOS production route, including capture consent, second-clock behavior, fan-out semantics and failure recovery. Record the chosen source of physical microphone identity and the rule for default-device changes. Do this before changing production audio code.
2. **Rust route core.** Add a separate module/service and fake CPAL ports. Port only reviewed probe logic. Test queue bounds, overflow/underflow, drift correction, channel/sample conversion, gain/clipping, callback allocation safety, device failure, stale events, and clean shutdown. No IPC or UI in this change.
3. **Typed control IPC and session state.** Add `start_call_routing({ outputDeviceId })`, `stop_call_routing()`, and `call_routing_status()` plus a typed `CallRoutingChanged` event through `ipc.rs` and generated bindings. `Start` is the explicit capture command. State and errors are backend-owned; selected output remains session-only. Revalidate the ID at Start and after Refresh. No SQLite migration or telemetry. Review the macOS `NSMicrophoneUsageDescription` text and OS microphone authorization flow as a separate permission change before this PR. Confirm whether any Tauri capability change is actually necessary; do not grant broad shell, filesystem, or network access.
4. **Library fan-out and UI.** Reuse validated library sounds and play-mode decisions for both sinks, with route-specific resampling/cache limits. Keep local status separate from routing status. In Settings show selected, starting, active, failed and stopped states with explicit Start/Stop, permission/device errors, keyboard and screen-reader feedback, EN/UK text, and Dark/Light/System compatibility. In Library show route failure without suppressing local Play. Do not show `Discord Verified` from stream state. Add component and IPC tests for races and stop behavior.
5. **Hardware evidence and release gate.** On macOS 14+ arm64 and x64, verify physical mic only, clip only, combined voice and clip both during phrase and quiet gaps, local clip only, Stop capture, hotplug, sleep/wake, device loss and restart, with the actual virtual input selected in Discord and Meet. Record device/configuration, queue/drift metrics and any measured latency; do not infer latency from nominal buffers. Include a real remote recipient before claiming call delivery. Run a sustained test before release. Separately satisfy ADR 0016's signed/notarized installer, GPL source, coexistence, repair, upgrade, removal and rollback gates before bundling ScreamPad Audio.

## Acceptance and current evidence

The production MVP is ready for release consideration only when local playback works without the component; capture starts only from an explicit user action and stops on every exit/error path; an active route sends mic and selected library sounds without leaking mic to local output; and the hardware and call-app checks above pass on supported macOS targets. A failed call route is visible and recoverable without breaking local playback.

The development Mac has enumerated original BlackHole and unsigned ScreamPad Audio side by side. Isolated Discord Mic Test heard clip-only speech and mic-only voice. Combined voice was audible only during phrase segments in repeated tests; the cause is unresolved despite nonzero virtual-input levels during quiet gaps. Local monitoring and a remote call recipient are **NOT VERIFIED**. PR #50 adds isolated gain/meter instrumentation and passed CI; it is not a production fix or proof of combined routing. Windows, signed distribution, macOS 14, x64 runtime, and end-to-end Discord/Meet delivery are **NOT VERIFIED**.
