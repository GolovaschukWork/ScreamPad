# ADR 0010: Application Settings and Per-Sound Playback Options

- Status: Proposed (awaiting owner decision; schema 2 needs explicit approval)
- Date: 2026-10-25
- Owner: project owner

## Context
Schema 1 has one table, `sounds`. Three product needs have no storage yet:
- the chosen UI language (ADR 0008 deferred the switcher until a `settings` migration is approved);
- a master volume that survives restarts;
- per-sound options: a gain trim and what happens when a sound is triggered again while it is still playing.

Rules that apply: migration `0001` is released and must not be edited; schema changes are forward-only migrations that need
owner approval, a `SHIPPED_CHECKSUMS` entry and a frozen `schema_v2.sql` fixture. The existing pre-upgrade `VACUUM INTO` backup
covers the 1 -> 2 step.

## Options
### Settings storage
- **A: typed single-row table `app_settings`** (recommended). One row, `CHECK (id = 1)`, one typed column per setting, every
  column with a default and a range check. Invalid values are rejected by the database.
- **B: key-value table.** Adding a setting needs no migration, but values are untyped text, ranges cannot be enforced by
  `CHECK`, and typos in keys fail silently. Rejected.

### Per-sound options
- **A: new columns on `sounds`** via `ALTER TABLE ... ADD COLUMN` (recommended). The immutability trigger lists the media
  columns explicitly, so the new columns stay editable. Existing rows receive the defaults.
- **B: separate `sound_options` table.** An extra join and a second row to keep in step with every sound, for options that are
  always present. Rejected until options become sparse or numerous.

## Proposed schema 2 (SQL)
```sql
ALTER TABLE sounds ADD COLUMN gain_millibels INTEGER NOT NULL DEFAULT 0
    CHECK (gain_millibels BETWEEN -6000 AND 600);
ALTER TABLE sounds ADD COLUMN play_mode TEXT NOT NULL DEFAULT 'overlap'
    CHECK (play_mode IN ('overlap', 'restart', 'ignore', 'toggle'));

CREATE TABLE app_settings (
    id                    INTEGER PRIMARY KEY CHECK (id = 1),
    language              TEXT    NOT NULL DEFAULT 'system'
        CHECK (language = 'system' OR (length(language) BETWEEN 2 AND 8 AND language NOT GLOB '*[^a-z-]*')),
    master_gain_millibels INTEGER NOT NULL DEFAULT 0 CHECK (master_gain_millibels BETWEEN -6000 AND 0),
    updated_at_ms         INTEGER NOT NULL DEFAULT 0 CHECK (updated_at_ms >= 0)
) STRICT;
INSERT INTO app_settings (id) VALUES (1);
```
Units: gain in millibels (1/100 dB) so values are integers.

## Decision (proposed)
- `language` is validated loosely in the database (`system` or a lowercase tag shape) and against the supported list
  (`en`, `uk`) in the application layer, so adding a language needs no migration.
- Per-sound gain range is -60 dB .. +6 dB; the master gain is -60 dB .. 0 dB (no boost on the master, to avoid clipping).
- Play modes: `overlap` (default, start another voice), `restart` (stop the playing voice, start again), `ignore` (do nothing
  while playing), `toggle` (a second trigger stops it).
- Loop is **deferred** to its own later migration.
- New typed commands: `get_settings`, `update_settings`, `set_sound_options`; DTOs generated by tauri-specta (ADR 0004). The
  frontend loads settings before the first render so the language does not flash.

## Consequences
- Playback must track voices per sound: `engine.play` needs the sound id and the mixer must report voice ids and end events so
  `restart`, `ignore` and `toggle` can be decided in `PlaybackService` (not in the audio callback).
- The mixer applies per-voice gain (already supported) and master gain (already supported); no new real-time work, no SQLite on
  the audio thread.
- Gain above 0 dB can clip; the existing soft limiting/clamping behaviour must be checked with a test at +6 dB.
- Downgrading to an older build is not supported (forward-only migrations).

## Validation (to be done after approval)
- Frozen fixture `schema_v2.sql`, `SHIPPED_CHECKSUMS` entry, upgrade test 1 -> 2 with data, rollback on failure.
- Constraint tests: out-of-range gain, unknown play mode, wrong storage type, second settings row, deleting the settings row.
- Verified so far (executed, SQLite CLI, in memory, on the real `0001` schema): existing rows get the defaults; valid updates pass;
  media columns remain immutable; invalid gain, play mode, language and a second settings row are rejected; `integrity_check` ok.
  This does not test the Rust migration runner.
- NOT VERIFIED: behaviour on Windows, the audible effect of gain and play modes.

## Questions for the owner
1. Typed single-row `app_settings` (recommended) or a key-value table?
2. Per-sound options as columns on `sounds` (recommended) or a separate table?
3. Gain range: maximum +6 dB (recommended) or +12 dB?
4. Play-mode set (`overlap`, `restart`, `ignore`, `toggle`) and default `overlap`: accepted?
5. Store the master volume (recommended) or reset it on each start?
6. Loop deferred to a later migration: accepted?
